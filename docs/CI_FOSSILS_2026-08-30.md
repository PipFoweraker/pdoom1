# CI fossils -- what was deleted, and the rule that replaces declaring them

Written 2026-08-30, immediately before the deletion it records, so that removing
1,334 workflow runs destroys no evidence. Every number below has a command.

A **fossil** is a red whose trigger can no longer fire. It is not a chronic red:
its streak is frozen, so it can never clear, and no fix exists that would clear
it. Two ways a pair becomes one:

- the workflow **file** is gone from the repository, but the Actions API keeps
  serving its run history; or
- the file is present and no longer **declares that trigger**.

`tools/check_chronic_red.py` learned to tell fossils from chronic reds on
2026-08-29 (#1336), after its first version declared three of them as chronic --
which would have carried three `DECLARED` entries that could never go stale, the
permanent register of permanent reds the shrink-only rule exists to prevent.

## The ruling

Pip, 2026-08-30, asked whether fossils should be relegated out of existence or
freshened into live tests again, and answered his own question:

> "removing them entirely so we're not training ourselves to ignore reds on
> fossils seems like the best play."

RULING: 2026-08-30 -- a CI fossil must be removed entirely, never declared: a red that cannot clear trains the team to discount reds, and a declaration for one can never go stale, so the register of exceptions would grow forever -- flavour: guard-doctrine -- mechanism: tools/check_chronic_red.py --check fails on any fossil, so a new one must be purged or its trigger restored

`check_chronic_red.py` therefore now **fails** on a fossil rather than listing it,
with two acceptable remedies: delete the frozen runs, or restore the trigger so
the pair is live again and its red means something.

## What was deleted

Measured 2026-08-30, immediately before deletion:

    gh api "repos/:owner/:repo/actions/workflows?per_page=100" \
      --jq '.workflows[] | "\(.id)  \(.path)"'

### `deploy-dreamhost.yml` (workflow id 189152497) -- 336 runs

| | |
|---|---|
| runs | **336** |
| conclusions | `failure: 336` |
| events | `push: 334`, `workflow_dispatch: 2` |
| range | 2025-09-14 .. 2026-06-26 |

**It never succeeded once, in 336 attempts, over nine months.**

The file was deleted from `main` on 2026-02-03 in `586140af` ("fix: Clean up and
fix CI workflows"), and `git ls-files .github/workflows/ | grep dreamhost`
returns nothing. Runs continue to 2026-06-26 because a workflow file still
present on a non-default branch runs on pushes to that branch; the Actions API
lists the workflow as `active` regardless, on the strength of the run history
alone. Deleting the runs removes the workflow from the Actions list entirely,
which is the only way to retire it -- there is no "delete workflow" endpoint.

### `dev-blog-automation.yml` (workflow id 188929370) -- 998 runs

| | |
|---|---|
| runs | **998** |
| conclusions | `failure: 976`, `startup_failure: 1`, `success: 21` |
| events | `push: 706`, `pull_request: 291`, `workflow_dispatch: 1` |
| range | 2025-09-13 .. 2026-07-28 |

The file **stays**. It was deliberately made `workflow_dispatch`-only on
2026-07-29, and its own header says why:

> autogenerated devblog posts are NOT to be published. This workflow's
> create-dev-blog-entry job pushes to main, which in turn trips
> sync-dev-blog.yml and publishes to the public pdoom1-website repo. It has
> never actually run to completion (create-dev-blog-entry is missing its
> gitpython install, and the generated markdown is indent-mangled), so nothing
> has shipped -- but a naive "fix the import" would have started
> auto-publishing.

Its last `push` and `pull_request` runs are 2026-07-28 -- **the day before** the
triggers were removed. Every one of those 997 runs is frozen.

**On the 21 successes.** They are all `push` runs between 2026-06-27 and
2026-07-17, and they are not evidence that the automation worked: the workflow
has never run to completion, so a green run means the jobs that did run passed
while the one that matters did not do its job. Deleting them loses no proof of a
working feature, and keeping 21 greens while deleting 976 reds would be editing
the record to flatter it.

Repair of the generator remains tracked in **#1009** (draft-generator only). That
issue is unaffected: the file, its `workflow_dispatch` trigger and its jobs all
survive this. Only the frozen run history goes.

## What was NOT deleted

- **`docs-sync.yml:pull_request`** -- 39-for-39 red and the one genuine chronic
  red in the repository (#1279). Its trigger is **live**, so its red still means
  something and can still clear. It stays declared, not purged.
- Any workflow file. This deletion touches run history only.
- `release-ledger.yml:schedule`, which cleared itself on 2026-08-29 when its
  04:23 UTC cron went green for the first time since 2026-08-24.

## The state this leaves

    python tools/check_chronic_red.py --check

    before: 1 chronic (declared), 3 fossils
    after:  1 chronic (declared), 0 fossils

## Why this is worth 1,334 deletions

The Actions page is a signal surface. Two workflows on it had been red
continuously for months -- one of them for nine months without a single success --
and neither could ever go green, because neither could run. Every reader who
learned to skip those two rows was being trained, correctly, that a red row on
this page does not necessarily mean anything. That training is the cost, and it
is paid by the next real failure.

`release-ledger.yml` already paid it once: red for five days on an unsatisfiable
gate, so its red for a genuine reason on 2026-08-28 -- v0.14.4 tagged and never
published -- was indistinguishable from the noise and went unread overnight.
