DECISION CARD  ·  DEV POWERS IN AN ALPHA
Sat 1 Aug 2026, 09:05. Pip's question, verbatim: "what is the right nomenclature to use if I am shipping an alpha build that has a tool that lets players do things they won't be able to do in the full version of the game? I don't mind players having dev / mod powers during an alpha."

The short answer

The naming is the small half. The contract is the big half, and you have already built it twice.

Players do not actually need to know whether a power is "dev", "debug", "mod" or "cheat". They need to know three things, and every good implementation of this in the industry answers exactly these:

  1. Does this count? (leaderboard, achievements, records)
  2. Is this permanent? (will it exist in the finished game)
  3. Did I turn it on by accident? (can I tell, later, that this run was touched)

A run that answers those three clearly can hand the player almost any power without damaging anything. A run that leaves them ambiguous corrupts your data and the player's sense of their own achievement, no matter what the button is called.

The mechanism already exists in this codebase

On 2026-07-31 you ruled on a structurally identical problem. Scenario packs (Sandbox Mode opens with $10,000,000) let players do things that make their score incomparable. The ruling was not to remove them:

"I want scenarios to lock you out of the board and for players to be warned about it explicitly when picking them. I have no problems with the scenario, the player just needs to be actively warned."

That shipped as #1060, and it is a reusable pattern rather than a one-off:

PieceWhere it livesWhat it does
GameConfig.is_ranked_run()autoload, single source of truthevery board-write routes through it
Amber [!] NOT RANKED linepre-game screen, on selectionwarns at the moment of choice
Amber game-over noticegame-over screenwarns again, visibly, rather than failing silently

Dev powers are the same shape. The cheapest correct answer is not a new system -- it is one more input to is_ranked_run(). Same warning colour, same wording pattern, same choke point.

One important difference, and it changes the design. A scenario is chosen before the run starts, so a single pre-game check is enough. A dev power can be used mid-run, at turn 30, after 20 honest turns. So the flag must be sticky and one-way: once this run has touched a dev power, it is unranked for good, and turning the tool back off does not restore it. Otherwise the exploit is trivial and, worse, accidental.

What the industry actually does, and what to steal

GameWhat it is calledThe mechanism worth stealing
Minecraft "Allow Cheats" A flag on the world, not the build. Set at creation, shown in the world list forever, disables achievements. The player can always see which of their worlds is "tainted".
Factorio "This save has been marked as cheated" Irreversible. One console command permanently marks the save and kills achievements. No path back. This is the sticky-flag pattern, and it is the right one.
Kerbal Space Program "Cheats" / "Debug Toolbar" Kept openly, documented, no shame framing. Players use it to learn, and nobody pretends otherwise.
Slay the Spire "Custom Mode" Name describes what it is, not who it is for. Runs are simply not scored. No pejorative.

Common thread: the flag belongs to the RUN, not the BUILD, it is visible after the fact, and the naming is descriptive rather than apologetic. None of them call it "dev mode" to players, because "dev" describes who wrote it, not what it does.

Naming options

NameForAgainst
Dev Tools Honest, signals transience, matches your internal language. "Dev" describes the author, not the function. Slight "you are not meant to be here" flavour, which you do not want if you are happy for alpha players to use it.
Lab Tools (or Lab Overrides) In-fiction. You run an AI lab; the settings screen is already called LABORATORY SETTINGS. Costs no immersion and needs no apology. Slightly less obvious that it is temporary -- must be carried by the tooltip.
Alpha Tools Transience is in the name, which is exactly the property you asked for. Self-deprecating in a way alpha players find charming rather than alarming. Dates the feature. You will have to rename or remove it at beta -- though arguably that is a feature, since it forces the decision.
Sandbox Widely understood. Already taken. "Sandbox Mode" is one of your scenario packs. Reusing it would collide, and collisions in this project have been expensive.
Recommendation: "Alpha Tools", styled in the same amber you already use for NOT RANKED, wired into is_ranked_run() as a sticky one-way flag.

"Alpha" does the transience work in the name itself, so the tooltip does not have to carry it alone, and it will not survive a beta by accident -- the name will look wrong the moment it stops being true. Reusing the amber is not laziness: you have now established amber as "this is off the record" in two places, and a third meaning for a fourth colour is how UI languages rot.

Argued against inventing a new colour or badge system. You have one already and it is only two days old.

The wording, if you want it ready-made

On the toggle:

[!] ALPHA TOOLS -- using any of these takes this run off the leaderboard, permanently. These tools will not exist in the finished game.

At the moment of first use, mid-run -- this is the one that matters, because it is the only place the player learns the flag is one-way:

[!] This run is now UNRANKED. Alpha Tools were used on turn 30. Turning them off does not undo this.

At game over -- shown, never silent:

NOT RANKED: Alpha Tools were used in this run. Play without them for the board.

This connects to an issue already open

#788 -- "Leaderboard: mark runs where dev mode was used (visible badge, NOT exclusion)", labelled ship:hotpatch-48h.

Note that #788 proposes mark, do not exclude, and this card proposes exclude and tell them. Those are genuinely different rulings and both are defensible:

  • Mark, do not exclude keeps the player's run visible and lets the reader judge. Kinder to the player. Requires the board to carry and render a flag, which is website work and touches the submission surface that #191 froze.
  • Exclude and tell them needs no board change at all -- it is entirely client-side, it is the pattern already shipped for scenarios, and it keeps the board's guarantee simple: every entry here is a clean Standard run.
Recommendation: exclude now, mark later. Excluding is free today and preserves the board's one strong claim while the player base is tiny. Marking becomes the better answer once the board is rich enough that losing entries costs more than the ambiguity does. Worth resolving #788 with that reasoning rather than leaving two contradictory rulings open.

One related thing to decide while you are here

PR #1079 (open, not merged) gates the DEV BUILD badge on OS.is_debug_build(). Side effect the agent flagged: the dev overlay, flight recorder, UI evolution recorder and perf log all gate on the same is_dev_build() -- so they were running in release builds until now, and that PR silently switches them off.

That is probably right and probably desirable -- players stop having invisible recorders writing to their disk. But it is a behaviour change well beyond a banner, and it is the same question this card is about: which capabilities are build-gated, which are run-gated, and which are player-facing on purpose. Worth deciding together rather than accepting one as a side effect of the other.
