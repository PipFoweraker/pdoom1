Card 1 -- What is the canonical source of "the current league seed"?

What happened

On league night the seed was blessed at ~18:45 as weekly-2026-w31. pdoom1.com went on serving the previous seed for roughly 90 minutes, with real scores sitting unpublished, until it was corrected by hand.

The board probe (scripts/check-board-liveness.py, website repo) is deliberately built to derive rather than hardcode. It draws candidate seeds from the anomaly captures, weekly/current.json, leaderboard.json and published-board.json. Every one of those is a record of a seed the site has already seen. A seed drawn for the first time at a ceremony appears in none of them.

So it probed 108 boards (6 seeds x 18 epochs), never asked about weekly-2026-w31, and reported OK: deployed board (weekly-2026-w30, L3) holds 3 entries. Green, confident, wrong.

The asymmetry that explains it, and it is the whole lesson. The epoch half of the board key is a counter (L3), so the probe scans a forward window and finds a bump automatically. The seed half is a drawn string. There is no "next" to look ahead to. You cannot enumerate a drawn value, and the moment a new one exists is exactly the moment nobody is watching.

The second, separate problem: two formats are live

ProducerFormatExampleHow it is obtained
The game
game_config.gd:462		 hyphens, lowercase w, not zero-padded weekly-2026-w31 DRAWN -- a hand-pinned const, changed by a human at a ceremony
The website
game-integration.py:470		 underscores, uppercase W, zero-padded weekly_2026_W31 COMPUTED -- datetime.isocalendar() at runtime

These disagree on punctuation, which is annoying. They also disagree on epistemology, which is fatal: one is a value a human chose, the other is a value a clock produced. On league night the site's computed week had already ticked to W32 while the blessed seed was w31. Even with identical formatting they would have disagreed. Any consumer that computes the seed will drift from the game, every time, forever.

Options

 OptionForAgainst
A Website parses FEATURED_SEED_OVERRIDE out of game_config.gd at the released tag Zero game-side change. The value is genuinely authoritative -- it is what the shipped client posts to. Parsing GDScript with a regex from another repo. Breaks silently if the const is renamed, moved, or made dynamic.
B Game publishes featured_seed + ladder_epoch in release_manifest.json, already a release asset Machine-readable JSON, already generated by CI on every tag, already carries commit_hash and engine. Small change. The release becomes the authority, which matches the standing rule that the game is the authority. Only updates at a tagged release. A seed rolled without a release would not appear.
C Game serves a small live league.json endpoint Always current, independent of release cadence. New infrastructure to host and keep up. More moving parts than the problem deserves right now.
D Keep deriving; add the blessed seed to a config the ceremony updates No cross-repo coupling. Puts a manual step inside the ceremony -- the exact thing that failed. Ceremonies forget.
Recommendation: B, with a rule attached.
release_manifest.json already ships on every tag and already carries provenance. Adding two fields makes it the single machine-readable answer to "what board is live", and it is discoverable without parsing another language.

The rule that matters more than the mechanism: a seed roll REQUIRES a release. That is already true in practice -- the seed is a pinned const inside the client, so rolling it without a rebuild produces a client that posts to the old board. Option B makes that existing constraint explicit and machine-checkable rather than tribal.

THE ASK -- Card 1

1a. Canonical source of the current seed:
A parse the tag   B release manifest (recommended)   C live endpoint   D ceremony config

1b. Canonical seed string format -- one of these becomes correct and the other becomes a bug:
weekly-2026-w31 (game's current form)    weekly_2026_W31 (website's current form)    something else: ......................

Note: changing the game's format changes the board key and would fork every existing board. If you pick the underscore form, that is an epoch-level event, not a rename. The cheap answer is almost certainly to make the game's existing form canonical and fix the website.

Card 2 -- What happens to a board when the seed rolls?

What happened, this morning

The website corrected itself overnight and now publishes weekly-2026-w31 / L3 with 3 entries, matching the score API exactly. That failure is closed.

But the board-liveness check is now failing with verdict orphaned-scores, and it is failing correctly. Rolling the seed left the previous board's entries recorded on a board the site no longer publishes: 

weekly-2026-w30 / L3   -- entries by "Applied AI Safety", "Intelligent Agents Studies"
                          dated 2026-07-30, now unpublished and unviewable

The probe's own words: "Players finished those runs. No visitor can see them, and no error was shown to anyone." That is exactly what it was built to shout about, and it is shouting about a consequence we chose deliberately -- the seed was rolled (#1047) specifically so the league would not open with prior runs already standing.

So the alarm is not wrong and the decision was not wrong. What is missing is a policy for the state in between. Right now every future seed roll will re-raise this, on a monthly cadence, forever -- and an alarm that fires predictably on an intended action is an alarm people learn to ignore. That is how #203 got ignored for two weeks.

Options

 OptionForAgainst
A Move rolled-off boards into the anomaly archive as acknowledged history (the mechanism already exists -- it currently holds 0 entries) Uses machinery that is already built. Silences the false alarm without hiding anything. Honest: the runs are recorded, just not current. "Anomaly" is the wrong word for a routine, intended roll. Risks the archive becoming a junk drawer.
B Publish past boards as browsable history; only the newest is "current" Nothing is ever orphaned. Players keep their runs visible. A league with history looks like a league rather than a demo. Real website work. Needs a UI decision about how past seasons are presented.
C Teach the probe that a superseded board is not an orphan, and check only the current one Smallest change. Kills the recurring false alarm immediately. Weakens the guard. "Superseded" and "we broke it" become indistinguishable -- the precise failure mode of #1027.
Recommendation: A now, B when there is a second real season.
A is minutes of work with existing machinery and stops the alarm crying wolf before the next roll. B is the right end state and becomes worth building the moment there is history anyone wants to look at -- which is not yet, with three entries.

Argued against: C. It fixes the symptom by lowering the standard. This project's whole diagnosis is that guards get quietly weakened until they report green about nothing.
