# Linking versions, ladder epochs and seeds out to v0.20 -- proposal

**Status: PROPOSAL. Three rulings are needed from Pip and are marked as such.**
Written 2026-08-24 off the mechanical sweep in `RELEASE_LEDGER.md`, which is
generated by `tools/check_release_ledger.py`.

---

## 1. What the sweep actually found

Nine values of `version.txt`, eight tagged and published, one not:

| | |
|---|---|
| Versions in history | 9 (`0.11.0` .. `0.14.3`) |
| Tagged **and** released | 8 |
| Bumped, never tagged | **1 -- `0.14.3`** |
| Ladder epochs cut | 6 (`L1` .. `L6`) |
| Featured seeds rolled | 5 (`w30` .. `w34`) |
| Minor versions in that span | 4 (`0.11`, `0.12`, `0.13`, `0.14`) |

Six ladder epochs across four minor versions, and **two of the six inside
`v0.14.x` alone** (L5 at v0.14.2 on 21 Aug, L6 on 23 Aug).

## 2. The model in the docs is wrong, and off-by-one undersells it

Issue #1152 records the ladder columns as "off by one from v0.14 down". The
sweep says the error is not arithmetic:

| Document | Says | Ground truth |
|---|---|---|
| `RELEASE_NOMENCLATURE.md` | v0.14 = **L3**, v0.15 = L4, v0.16 = L5 | v0.14.0 cut **L4** |
| `ROADMAP.md` | v0.14 = L4, v0.15 = **L5**, v0.16 = **L6** | L5 and L6 are **already spent**, both in August, both inside v0.14.x |

Both documents encode **one ladder epoch per minor version**. `ROADMAP.md`
forecasts L5 for v0.15 on 4 September; L5 was cut on 21 August and L6 two days
later. The forecast was not a week out, it was two epochs out, and it will be
wrong again by construction.

**The generator.** `BUILD_VS_LADDER_VERSION_SPLIT.md` 3.1 defines the ladder
bump as: *two identical inputs could produce a different score, trajectory or
RNG stream than the previous epoch*. That is a property of **gameplay change**.
The minor version is a property of **release cadence** -- a monthly train, first
Friday. These are independent axes. Any table with one row per minor version and
one ladder cell in it is asserting a coupling the codebase does not have, and
`tools/check_ladder_bump.py` will keep making that assertion false.

**RULING NEEDED (1).** Is the coupling one-directional? The evidence supports:

> *A minor version bump always cuts the ladder. The ladder may ALSO cut
> mid-version, as often as gameplay forks require. Therefore
> ladder epochs >= minor versions, always, and the ladder number is never
> forecastable.*

That is descriptively true of every release so far -- v0.13.0 cut L2, v0.14.0
cut L4, and L3/L5/L6 were mid-version forks. Adopting it means the forward
tables **must stop carrying a predicted ladder number**, which is the actual
fix to #1152.

## 3. The seed is a hand-typed literal with no generator and no guard

`FEATURED_SEED_OVERRIDE` is a string constant in `game_config.gd`. Nothing
derives it, nothing checks it, and the convention it follows is **written down
nowhere** -- I grepped `RELEASE_NOMENCLATURE.md`, `BUILD_VS_LADDER_VERSION_SPLIT.md`
and every ritual sheet, and found only examples.

From the five rolls, the convention is evidently *"name the ISO week the league
opens in"*:

| Seed | Set on | ISO week of that date | Match |
|---|---|---|---|
| `weekly-2026-w30` | 2026-07-24 | w30 | yes |
| `weekly-2026-w31` | 2026-07-31 | w31 | yes |
| `weekly-2026-w32` | 2026-08-07 | w32 | yes |
| `weekly-2026-w33` | 2026-08-13 | w33 | yes |
| `weekly-2026-w34` | 2026-08-23 | w34 | yes, **on the last day of w34** |

And `gate_5_seed_blessing.md` records the precedent directly: on 2026-07-30 the
const still read `weekly-2026-w30` and *"it was corrected to `weekly-2026-w31`
before that cut"* -- a stale week number was treated as a defect to fix before
cutting, not a cosmetic detail.

**So, flagged before Gate 5 is performed and not after:** today is Monday
2026-08-24, **ISO week 35**. The live const reads `weekly-2026-w34`. If the next
league opens on Friday 2026-08-28 -- also week 35 -- then by the 2026-07-30
precedent the seed about to be blessed is one week stale, and blessing it stamps
that into a public board key that cannot be tidied afterwards
(*"filtering standings is editing them"*).

I am not asserting this is wrong. The convention is undocumented, so this is
precedent plus inference, and it is Pip's call. But it is cheap to settle now
and expensive to settle after the board opens.

**RULING NEEDED (2).** Either:

- (a) the seed names the ISO week the league OPENS in -- in which case roll to
  `weekly-2026-w35` before Gate 5, re-merge, **re-cut** (Gate 5's own rule: a
  const change after the cut means you do not have a proven build); or
- (b) the seed names the week it was DRAWN in, and `w34` blessed in w35 is
  correct -- in which case write that sentence down, because nothing currently
  says it.

Whichever is ruled, it should then be **mechanised**: derive the expected seed
from the date and have `check_release_ledger.py` (or the Gate 5 sheet's check 2)
fail when the const disagrees, instead of relying on someone noticing. A
hand-typed literal governing a public board key is the same shape as a
hand-maintained index, and this repo's own anti-rot pattern says generate it.

## 4. The forward table, with three different kinds of certainty in it

The reason previous tables rotted is that they mixed a calendar (derivable), a
plan (a decision), and a consequence of gameplay (unknowable in advance) into
one row and rendered all three in the same typeface.

**SCHEDULED -- mechanically derivable, no judgement.** Monthly train, first
Friday, per `ROADMAP.md`:

| Version | Target date | ISO week | Expected seed at open |
|---|---|---|---|
| v0.15 | Fri 2026-09-04 | w36 | `weekly-2026-w36` |
| v0.16 | Fri 2026-10-02 | w40 | `weekly-2026-w40` |
| v0.17 | Fri 2026-11-06 | w45 | `weekly-2026-w45` |
| v0.18 | Fri 2026-12-04 | w49 | `weekly-2026-w49` |
| v0.19 | Fri 2027-01-01 | w53 | `weekly-2027-w53` |
| v0.20 | Fri 2027-02-05 | w05 | `weekly-2027-w05` |

Interleaved weekly seeds between those dates are the remaining Fridays and are
equally derivable: w35, w37, w38, w39, w41, w42, w43, w44, w46, w47, w48, and so
on.

Two things in that table are traps and are called out rather than smoothed:

- **v0.19 falls on Friday 1 January 2027.** New Year's Day. A monthly-train rule
  applied blindly puts an epoch cut and a league open on a public holiday.
  **RULING NEEDED (3):** hold v0.19 to 2027-01-08 (w02), or accept 1 January.
- **`weekly-2027-w53`** is not a typo -- 1 January 2027 is in **ISO week 53 of
  2026**, not week 1 of 2027. Any seed generator that formats
  `f"weekly-{year}-w{week}"` from a naive `date.year` will emit
  `weekly-2027-w53`, which is a week that does not exist. Use
  `isocalendar()[0]` for the year, not `.year`. This is a live bug waiting in
  any generator written for ruling (2) above, and it fires exactly once, in
  January, on a league night.

**FORECAST -- a plan, revisable, owned by Pip.** Theme names for v0.15+ are
provisional and `RELEASE_NOMENCLATURE.md` already says Pip names them. Nothing
here changes that.

**NOT FORECASTABLE -- and the table must say so.** The ladder epoch. As of
2026-08-24 the floor is **L6**. Every future row should read `>= L6`, ratcheting
as epochs are cut, and **never** a specific predicted number. That is the change
that stops #1152 recurring: not correcting the numbers, but deleting the column
that cannot be right.

## 5. Atomisation, and who rules the store

Under the atomise protocol clause 3 (ruled 2026-08-24: *"do not build an atom
store unless a named party will rule it -- if none exists, do not build the
store"*), the store proposed here is `docs/releases/releases.json`, schema
`pdoom.releases/0.1`, and the **named ruler is Pip Foweraker**, stated at build
time as the protocol requires. Intended eventual owner: the Orchestrator role,
which does not exist yet.

One atom per version bump, carrying: version, bump commit and date, ladder epoch
at bump, featured seed at bump, board key, tag state, release state. It is
generated, never hand-edited, and `--check` blocks stale commits -- the same
anti-rot pattern as `DQ_INDEX.md`, `RULINGS.md` and the commitment calendar,
and the opposite of the hand-maintained tables in section 2 that rotted.

**Deliberately NOT atomised yet:** anything the store cannot derive. There is no
`cut_commit` field, because the commit a build was cut from is recorded only
inside the `.pck` build stamp and is not reachable from git history. Inventing
the field and filling it with the bump commit would be the manufactured-
confidence shape again -- a value meaning "I could not tell" rendered as a value
meaning "fine".
