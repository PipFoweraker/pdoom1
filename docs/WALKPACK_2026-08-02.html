#1075 -- one signature, five times (Beacon terminal)

The rule, stated better than I stated it:

A check whose input is derived from the system it is checking cannot detect the class of failure that changes that input.

Five instances, across two systems sharing no code, no language, and no author. Every one produced a confident green light. As they put it: "it does not look like a gap in coverage, it looks like coverage."

Once is a bug. Five is a design defect in how checks get built. If the postmortem produces one durable artefact, this sentence with its five instances underneath is the candidate -- because unlike a metaphor, you can audit for it.

THIS ONE NEEDS ACTION -- not a lesson, an open item

#1074 reported that a compensation document "was never committed and no exposure occurred". All three clauses were wrong. Per beacon-internal/operations/Mistakes.md:

  • It was committed -- swept in by git add -A operations/
  • It was pushed to origin, in PR #17
  • Window ~2 minutes, closed by force-push

A residual remains. GitHub retains force-pushed commits. Orphaned commit b68d6d3 reportedly still contains it. A force-push does not delete anything on GitHub -- the commit stays reachable by SHA until GitHub garbage-collects, which for a public repo can be indefinite. Closing this properly means GitHub Support, or treating the content as disclosed and rotating whatever it exposed.

Raise with beacon-internal. Not a pdoom1 item, and not one to leave in a postmortem doc as history.
