# DESIGN -- splitting the publishing lanes

**Status:** design document. No code changes accompany it. Written 2026-08-24
against the state of `main` at `28f8cd94`, after v0.14.3 published Windows and
Linux, advertised a macOS download that 404s, and went red at the last job.

**Standing issues this builds on rather than re-derives:** #917 (robust
cross-OS releases), #1071 (no macOS build has ever been verified to run),
#1017 (FIRST-RUN.txt reaches nobody), #1069 (the ruling that made macOS
best-effort), #963 (the feed advertised URLs that never existed).

**Ladder-Impact: none.** Argued in section 7, not assumed.

---

## 1. What exists today

No proposals in this section. Every claim below is from a file in this repo,
the v0.14.3 workflow run (`32690368004`), or the published v0.14.3 assets.

### 1.1 The workflow and its jobs

`.github/workflows/enhanced-release.yml`, triggered on `push` of a `v*.*.*`
tag (or `workflow_dispatch`). Eight jobs:

| Job id | Display name | Runner | Needs |
|---|---|---|---|
| `validate-data` | Validate Historical Data & Schemas | ubuntu-latest | -- |
| `build-godot` | Build Godot Game (All Platforms) | ubuntu-latest | `validate-data` |
| `generate-feeds` | Generate Release Feeds & Metadata | ubuntu-latest | `validate-data`, `build-godot` |
| `create-release-manifest` | Create Release Manifest | ubuntu-latest | + `generate-feeds` |
| `create-github-release` | Create GitHub Release | ubuntu-latest | + `create-release-manifest` |
| `verify-release-urls` | Verify Release Download URLs | ubuntu-latest | `create-github-release` |
| `sync-website-version` | Sync Version to Website | (reusable call) | `create-github-release` |
| `deploy-feeds` / `notification` | Deploy Feeds / Send Release Notifications | ubuntu-latest | `create-github-release` |

Total wall clock for the v0.14.3 run: **5m36s**.

### 1.2 The single build job

`build-godot` runs `python scripts/build_all_platforms.py --version <tag>`,
which shells out to `tools/build_release.py` once per preset, **sequentially**.
The sequencing is deliberate and documented in both files: every
`build_release.py` invocation deletes `godot/.godot`, so two exports sharing one
workspace would destroy each other's import caches.

Failure policy, ruled in #1069 and encoded in
`MultiPlatformBuilder.REQUIRED_PLATFORMS = {"Windows", "Linux"}`: a Windows or
Linux export failure fails the job and nothing publishes; a macOS failure emits
a warning, discards the macOS outputs, and lets the rest continue.

Three `actions/upload-artifact@v7` steps follow, named `build-windows`,
`build-linux`, `build-mac`. The first two are `if-no-files-found: error`; the
macOS one is `if-no-files-found: warn`.

### 1.4 The four documents that then asserted macOS shipped

This is the actual defect, and it is not in the build.

1. **`public/releases/v0.14.3.json`** -- generated by
   `scripts/generate_release_metadata.py`. Its `downloads` and
   `metadata.platforms` blocks are **hardcoded literals** (lines 181-194):

   ```python
   "downloads": {
       "windows": f"{base_url}/PDoom-Windows-{version}.zip",
       "linux":   f"{base_url}/PDoom-Linux-{version}.zip",
       "mac":     f"{base_url}/PDoom-macOS-{version}.zip",
       ...
   },
   "metadata": { ..., "platforms": ["Windows", "Linux", "macOS"], ... }
   ```

   The `generate-feeds` job has **no `download-artifact` step**, so it has no
   way to know what was built. It runs before the release object exists, so it
   cannot read the release either. It is structurally blind.

2. **`release_manifest.json`** -- generated by
   `scripts/generate_release_manifest.py`. Its `assets` list IS derived
   (`collect_assets()` hashes every `*.zip` under `--assets-dir`) and correctly
   contains four Windows/Linux entries and no macOS entry. Two fields below it,
   `"platforms": ["windows", "linux", "macos"]` is a hardcoded literal
   (line 214). The same file tells the truth and a lie about the same subject.

3. **The `notification` job** echoes the literal string
   `"Game builds created for Windows, Linux, and macOS"`.

4. **The release body** carries the macOS Gatekeeper section from
   `tools/release_notes/RELEASE-BODY-security-notice.md`, unconditionally --
   instructions for a build that does not exist. pdoom1.com republishes release
   bodies verbatim at `/game-changelog/`.

### 1.5 What caught it, and when

`verify-release-urls` failed. From the log:

```
[!] v0.14.3.mac  404 (Not Found)
    https://github.com/PipFoweraker/pdoom1/releases/download/v0.14.3/PDoom-macOS-v0.14.3.zip
```

Two facts about that job worth carrying forward:

- It runs **after** `create-github-release`, by design (the tag must exist for
  the URLs to be checkable). So it reports, it does not prevent.
- The job has two checks in **sequential steps**: the feed check
  (`verify_release_urls.py --file`) and the unversioned-alias check
  (`PDoom-Windows.zip` / `PDoom-Linux.zip` / `PDoom.app.zip` must each 200).
  The feed check failed, so **the alias check never executed**. The second
  guard is masked by the first whenever both would fail for the same reason.

### 1.6 What the website did, without a human

`pdoom1-website/scripts/update-version-info.py` -> `derive_platforms(assets)`
attributes each release asset name to an OS by regex, requiring a build suffix
and rejecting names another OS claims explicitly. It wrote:

```json
"platforms": { "windows": true, "macos": false, "linux": true }
```

into `public/data/version.json`. `scripts/check-platform-claims.py` and
`scripts/check-campaign-facts.py` both read that field as the authority on what
shipped. The download button's `resolveDownloads()` in `index.html` uses the
same filename heuristics, kept deliberately in step.

**The website consumes the release's asset list, not our feed's `downloads`
block.** That is why it self-healed today while our own documents did not.
Its docstring already names the rule the game repo is missing: *"A platform is
'available' iff a matching downloadable build exists -- the one un-fakeable
source of truth (the file is either in the release or it is not)."*

Refresh path: `sync-game-version.yml` sends one `repository_dispatch` to
pdoom1-website (`gh api .../actions/runs?event=repository_dispatch` returns
`total_count: 2` as of writing, so this path has now executed). The backstop is
`auto-update-data.yml` on `cron: '0 */6 * * *'`.

### 1.7 The standing macOS facts

From #1071, verified 2026-07-31 and unchanged:

- `libgodotsteam.macos.template_release.framework/Versions/Current` must be a
  **symlink** to `Versions/A`. Git on Windows cannot carry it, so the repo
  holds a real directory. A Linux checkout reproduces the same shape, which is
  why CI fails the same way a Windows local build does.
- The framework has no `Info.plist`; Godot generates one and derives
  `CFBundleExecutable` by truncating at the first dot, looking for
  `libgodotsteam` when the binary is `libgodotsteam.macos.template_release`.
- `export_presets.cfg` sets `codesign/identity=""` and `notarization=0`.
- **No macOS build of this game has ever been proven to launch, on any
  release.** Not claimed broken -- claimed unchecked.

## 2. What "trifurcate" could mean

The word conflates three separable axes. Naming them first is most of the
design work, because only one of them is broken.

| Axis | Question | State today |
|---|---|---|
| **(a) Build parallelism** | Where does each export run? | one job, sequential |
| **(b) Publish independence** | Can one release gain assets over time? | no -- one publish |
| **(c) Reporting granularity** | Can a reader tell per-platform state? | **no -- four documents assert all three unconditionally** |

**Blunt version: splitting the build job would not have prevented today's
incident.** The build lane already isolates macOS correctly. Axis (c) is what
failed, and axis (c) is orthogonal to both others -- it can be fixed without
touching either.

## 3. The shapes

### Shape A -- three parallel JOBS in one workflow

A `strategy.matrix` over `[windows, linux, macos]` on `build-godot`, or three
explicitly-named jobs. `generate-feeds` fans in and reads `needs.*.result`.

**Correction to a comment that reads the wrong way.** Both
`build_all_platforms.py` and `enhanced-release.yml` say the platform builds
"MUST STAY sequential". That is true of parallel **processes sharing one
workspace** -- the `rm -rf godot/.godot` collision. Parallel **jobs** get one
runner and one workspace each, so the hazard does not apply. The comment should
be reworded when this lands, or the next reader will conclude the split is
forbidden.

- **Complexity cost:** low-moderate. Three copies of checkout + `setup-godot`
  (with `include-templates: true`) + Python setup. One fan-in point.
- **CI minutes:** this repo is **PUBLIC**, so standard Linux runners are
  unmetered. The real cost is three template downloads instead of one; the real
  gain is roughly 2 minutes of wall clock off a 5m36s run. Call it a wash.
- **Removes:** nothing that has failed. It makes a per-platform failure legible
  in the Actions UI as a distinct red job rather than a warning annotation
  buried in a green job's log -- which is a genuine, if modest, legibility win.
- **Introduces:** three artifact-presence conditions the downstream jobs must
  handle explicitly. If `generate-feeds` still hardcodes, nothing improves --
  the split creates the *opportunity* for truthful reporting, it does not
  deliver it.
- **Atomicity:** unchanged. Still one `create-github-release`. This is the
  important property: parallel BUILD, single PUBLISH keeps the release atomic.
- **"Not built yet" vs "never":** available at the fan-in
  (`needs.build-macos.result` is `success` / `failure` / `skipped`) but only if
  something writes it down.

### Shape B -- three independent WORKFLOWS publishing to a shared release

Each platform is its own `.yml`, triggered on the tag, each doing
`gh release upload` against the same release object.

- **Complexity cost:** highest, and the cost is not where it looks. The release
  object must exist before any lane uploads. Either a fourth "open the release"
  workflow owns creation (four workflows, not three), or the first lane to
  finish creates it -- and two `gh release create` calls against one tag race.
- **CI minutes:** similar to A. Not the constraint.
- **Removes:** one real capability nothing else gives -- **a macOS asset can be
  added days later, on a `macos-latest` runner, from the same tag, without
  recutting the release.** If macOS ever becomes buildable-but-slow, or
  needs a human in the loop before upload, this is the only shape that fits.
- **Introduces, and these are serious:**
  1. **A partial release that looks complete.** GitHub's release page has no
     "still building" state. A reader sees whatever assets exist and infers the
     set is final. Today's failure is at least loud (a red run, a 404 that a
     guard names); a quiet partial release is not.
  2. **Every derived document is generated once, at a moment when the asset set
     is not final.** `v0.14.3.json`, `release_manifest.json`, `releases.rss`,
     and the website's `version.json` all become stale the instant a late asset
     lands. Each needs a regeneration trigger, and each regeneration is a new
     way to produce a document that disagrees with its siblings.
  3. **The manifest's integrity anchor goes partial.** `release_manifest.json`
     carries per-asset sha256 and is the thing the self-updater is meant to
     verify against before trusting a blob. A manifest missing the asset a
     client is about to download cannot authorise that install. A late upload
     must rewrite the manifest, which changes the manifest hash printed in the
     already-published release body.
  4. **The website may not notice.** `sync-game-version.yml` fires on
     `release: published` / `edited`. Uploading an asset with `gh release
     upload` does not obviously fire either. **UNKNOWN** -- settled by one
     experiment: upload an asset to an existing test release and check whether
     a `release` workflow run appears. If it does not, the late lane must send
     the `repository_dispatch` itself; the 6-hour cron would otherwise be the
     only healer.
- **Atomicity:** destroyed unless replaced by an explicit contract (section 5).

### Shape C -- keep one build job, fix only the reporting

No structural change. `generate-feeds` gains a `download-artifact` step for
`build-*`; `generate_release_metadata.py` and `generate_release_manifest.py`
derive platform claims from the artifacts present; the notification echo stops
naming platforms it cannot see.

- **Complexity cost:** lowest. Three Python files, one workflow step, plus
  tests. `generate_release_manifest.py` already has
  `tests/test_generate_release_manifest.py` to extend.
- **CI minutes:** one artifact download, seconds.
- **Removes:** exactly today's failure -- and only today's failure. The feed
  would have listed two doors, both would have answered, and the run would have
  been **green and honest**. The website already behaves correctly and keeps
  behaving correctly.
- **Introduces:** nothing structural. One risk worth naming: derivation from an
  empty artifact set reads as "nothing shipped anywhere", which is the exact
  trap `derive_platforms()`'s docstring warns about. The required-platform check
  in `build-godot` (`if-no-files-found: error`) already prevents that from
  reaching the feed, but the feed generator should still refuse to emit a
  release with zero required platforms rather than emit an empty `downloads`.
- **Atomicity:** unchanged and intact.
- **"Not built yet" vs "never":** fully expressible, if the schema carries it.
  Under one atomic publish, "not built yet" never occurs -- the release is
  final the moment it exists. Every absent platform is `failed` or
  `unsupported`. That is a simpler world and it should be preserved as long as
  it is affordable.
- **What it does NOT do:** give macOS any path to ship. It makes macOS's
  absence honest, not fixed.

### Shape D -- the split that matches the failure

The three lanes are not three platforms.

```
  LANE 1  REQUIRED BUILDS      Windows + Linux, ubuntu-latest, cross-compiled.
                               Failure -> nothing publishes. (already true)

  LANE 2  UNVERIFIED BUILDS    macOS, macos-latest runner. Different runner,
                               different verification bar, different
                               consumer-facing status. Failure -> annotated,
                               release still publishes.

  LANE 3  PUBLISHED CLAIMS     feed JSON, manifest, RSS, release body,
                               website version.json. Derived from lanes 1-2,
                               never asserted. Failure -> release is wrong
                               even when both builds succeeded.
```

Lane 3 is invisible in the current design -- it is scattered across
`generate_release_metadata.py`, `generate_release_manifest.py`, a release-body
template and an echo statement, with no single place that knows what shipped.
That is why one macOS export failure produced four wrong documents.

Concretely, Shape D is Shape C's derivation plus Shape A's job split, with the
macOS job moved to `macos-latest`:

```yaml
# pseudocode, not a working file
jobs:
  build-required:
    runs-on: ubuntu-latest
    outputs: { windows: ..., linux: ... }      # shipped | failed
    # build_all_platforms.py --platforms Windows,Linux
    # any failure here fails the job; nothing downstream runs

  build-macos:
    runs-on: macos-latest
    continue-on-error: true
    outputs: { macos: ... }                    # shipped | failed
    # the .framework symlink exists natively here (#1071 cause 1)
    # a smoke launch is possible here and nowhere else

  publish:
    needs: [build-required, build-macos]
    if: needs.build-required.result == 'success'
    # 1. download build-* artifacts
    # 2. platform_status = derive_from(artifacts, needs.*.result)
    # 3. generate feed + manifest FROM platform_status  (lane 3, one source)
    # 4. create release with exactly the assets that exist
    # 5. verify: every advertised door answers AND every shipped asset is
    #    advertised
```

- **Complexity cost:** moderate. One new runner type, one derived status
  object, three generators reading it instead of asserting.
- **CI minutes:** macOS runners are billed at 10x on private repos. **This repo
  is public, so standard `macos-latest` runners are unmetered.** Verify before
  relying on it -- `gh api repos/PipFoweraker/pdoom1 --jq .visibility` returns
  `PUBLIC` today, and a repo going private silently changes this cost by an
  order of magnitude.
- **Removes:** both of #1071's causes at once (the symlink survives on a real
  macOS filesystem; ad-hoc codesign works natively), and creates the only place
  where "does the .app launch" can ever be answered automatically.
- **Introduces:** a second engine installation path (`setup-godot` on macOS),
  and the risk that a macOS build now **succeeds** and ships an artifact nobody
  has launched -- which is worse than not shipping, unless status carries
  `verified: false`. See section 4.
- **Atomicity:** intact. Still one publish.

## 4. Why macOS is asymmetric, argued

A design that treats macOS as the third element of a symmetric triple is wrong
on four independent axes. Any one of them would be enough.

**1. The failure is structural, not flaky.** Windows and Linux fail
occasionally and randomly. macOS fails **every time, for a known reason that
has nothing to do with the tagged source**: a `.framework` requires
`Versions/Current` to be a symlink, git-on-Windows cannot commit one, and the
Linux CI checkout faithfully reproduces the broken shape (#1071). A retry
policy is the correct response to flake and the wrong response to this. The
correct response is to change where it builds or what it vendors.

**2. A successful build would be an artifact of unknown value.** #1071's
conclusion, unchanged: no macOS build has ever been proven to launch, on any
release. Windows has Pip's own machine; Linux has a standing Debian tester
(#917). macOS has nobody, ever. So for macOS -- and only macOS -- `built` and
`runs` are genuinely different states, and the gap between them has never been
closed once. **A boolean cannot say "we built it and nobody knows if it
works."** Windows can live with a boolean. macOS cannot. That is the asymmetry
in one sentence.

**3. Published does not mean reachable.** Windows SmartScreen is a two-click
bypass documented in the release body. macOS Gatekeeper, unsigned and
un-notarised (`codesign/identity=""`, `notarization=0`), blocks first launch;
Sequoia removed the right-click-to-Open path that every guide on the internet
still teaches (#1017). The first Manifund backer hit exactly this, gave up, and
said so publicly. So the macOS lane's definition of done includes a document
(`FIRST-RUN.txt`, #1017) that the other two lanes do not need in the same way.

**4. It is not a rounding error.** #1017 measured macOS at ~35% of v0.13.1
downloads (Windows 7, macOS 6, Linux 4). The platform we have never verified is
the second most downloaded.

**The design consequence.** Per-platform state needs two orthogonal fields, not
one boolean:

```
  availability:  shipped | pending | failed | unsupported
  verification:  verified | unverified | unknown
```

macOS is the only platform for which the second field currently does real work.
Windows is `shipped` + `verified`; Linux is `shipped` + `verified`; macOS today
is `failed` + `unknown`, and after a `macos-latest` lane lands it would be
`shipped` + `unverified` -- which is precisely the state #917 clause 3 already
asked release notes to carry ("boots on X, not extensively tested").

## 5. The atomicity contract

Today's release is atomic: one build, one publish, one moment at which every
document is generated. That property is worth defending and should be given up
only for a payload that exists. The contract below preserves it under Shapes A,
C and D, and defines what Shape B would have to implement.

**R1. The release object is atomic; the platform set is not necessarily.**
One tag, one GitHub Release, created exactly once, by exactly one job.

**R2. Required platforms are present at creation or the release is not
created.** Already true (`REQUIRED_PLATFORMS = {"Windows", "Linux"}`,
`if-no-files-found: error`). Unchanged.

**R3. A document may never assert a platform it did not observe.** Every
platform claim in every generated artefact derives from the asset set. This is
the website's rule (`derive_platforms`) adopted upstream. Under R3 the four
lying documents of section 1.4 are unwritable.

**R4. A `downloads` block contains a key only when that platform is
`shipped`.** This kills the advertised-404 by construction, and it means
`verify_release_urls.py --file` needs **no change at all** -- it checks every
URL the feed lists, and the feed stops listing doors that were never built. The
guard did not fail today. Its input lied to it.

**R5. Absence is stated, not inferred.** Alongside `downloads`, every feed and
manifest carries an explicit block:

```json
"platform_status": {
  "windows": { "availability": "shipped", "verification": "verified" },
  "linux":   { "availability": "shipped", "verification": "verified" },
  "macos":   { "availability": "failed",  "verification": "unknown",
               "reason": "https://github.com/PipFoweraker/pdoom1/issues/1071" }
},
"platform_set_final": true
```

`platform_set_final: false` is the ONLY thing that lets a consumer distinguish
"not built yet" from "will never be built for this release". Under one atomic
publish it is always `true` and costs nothing. Under Shape B it is the entire
contract, and any lane that uploads late must flip it and regenerate every
document that carries it.

**R6. Consumer rules, stated once so three surfaces cannot drift.**

| Status | Website button | Feed `downloads` key | Release body section |
|---|---|---|---|
| `shipped` + `verified` | download | present | full instructions |
| `shipped` + `unverified` | download, labelled unverified | present | instructions + "not yet confirmed to launch" |
| `pending` | "building" | absent | absent |
| `failed` | "not available for this release" + issue link | absent | absent |
| `unsupported` | absent | absent | absent |

The release body is on that list on purpose. It shipped macOS Gatekeeper
instructions for a macOS build that does not exist, and pdoom1.com republishes
it verbatim.

**R7. The website contract is preserved, not replaced.**
`pdoom1-website/scripts/update-version-info.py::derive_platforms()` keeps
deriving from the release's asset list and stays the authority for
`latest_release.platforms`. It worked correctly today with no human
intervention, and asset-presence is the one un-fakeable signal. `platform_status`
is **additive** -- it carries the `verification` and `pending`/`failed`
distinction that an asset list structurally cannot express. If the website never
reads it, nothing regresses. That is the test of whether R5 was designed as an
addition or as a replacement.

## 6. Does Gate 6's "every advertised door answers" move?

`docs/rituals/gate_6_board_opens.md`, check 1, backed by
`verify_release_urls.py --file`, blocking.

**Under Shapes A, C and D: it does not move, and it does not change meaning.**
R4 makes "advertised" mean "listed in the feed's `downloads` block", which is
what the check already reads. What changes is that the block becomes derived,
so the clause becomes satisfiable rather than permanently false for macOS.

Three amendments the gate needs regardless of shape:

**6.1 Add the converse.** Check 1 catches advertising more than exists. Nothing
catches shipping an asset nobody is told about. Add: *every shipped asset
appears in `downloads`, and `platform_status` matches the release's actual
asset list.* One command, comparing `gh release view --json assets` against the
feed.

**6.2 Unmask the alias check.** The `PDoom.app.zip` alias check is a later
**step** in the same job as the feed check, so a feed failure prevents it
running -- which is what happened on v0.14.3. Put the two checks in separate
jobs, or make the first non-fatal within the job and gate on an aggregate.
This is a real bug in a guard, independent of any redesign.

**6.3 The alias check must become conditional.** It currently demands
`PDoom.app.zip` answer 200 unconditionally. Given #1071, that is a check that
**cannot pass on any release** until macOS is fixed -- so every release run is
guaranteed red for a known reason. A guard that is always red is a guard nobody
reads, and the next genuinely new failure arrives inside a red run that already
looked normal. This is alarm fatigue being manufactured deliberately. Make the
alias assertion fire only for platforms whose status is `shipped`, and let a
separate, explicitly-named check assert that macOS is still `failed` for the
reason we think.

**Under Shape B specifically:** the clause acquires a timing problem the
ceremony cannot solve. Gate 6 fires on a Friday evening wall clock; a lane that
publishes later can falsify a clause that was true when spoken. Shape B would
need check 1 re-run automatically at the moment the last lane finishes, plus a
seventh mechanical check at the gate: *the platform set for this build is
final, or names what is still pending.* That is a real amendment to the
ceremony, and it is a cost of Shape B rather than of the others.

## 7. Ladder impact -- none, and why

`tools/check_ladder_bump.py` requires a ladder bump or an explicit
`Ladder-Impact: none` declaration when anything under `godot/` changes outside
UI/scenes/assets/theme/tests/docs. Nothing proposed here touches `godot/` at
all: the changes live in `.github/workflows/`, `scripts/`, `tools/` and `docs/`.

The deeper reason, which matters more than the file-path rule: **the board key
is `(featured seed, ladder epoch)`, and both are compiled into the build from
the tagged source.** `FEATURED_SEED_OVERRIDE` is a const in
`godot/autoload/game_config.gd`; the epoch comes from `ladder_version.txt`. A
macOS player running v0.14.3 lands on `(weekly-2026-w35, L6)` exactly as a
Windows player does, because the key travels in the source, not in the
packaging. Which platform binaries a tag ships, and when, cannot fork a board.

That is also the permission that makes asynchronous platform lanes safe on the
ladder axis at all -- **provided any late lane builds from the same tag**, not
from a branch. A lane that rebuilds from `main` after `main` has moved would
ship a different seed or epoch under the same version string, which is the
v0.13.2 board-fork failure re-created by another route
(`docs/RELEASE_PLATFORMS.md`, failure 1). Any late-publishing lane must take a
tag as its only input.

## 8. Recommendation

**Do Shape C now. Do Shape D next. Do not do Shape B.**

**Shape C first, because it is the only one that addresses what broke.** The
build lane already handled macOS correctly on v0.14.3; four documents did not.
C makes those documents derived, costs three Python files plus one workflow
step, changes no structure, preserves atomicity, and would have turned today's
run green and honest. Every other shape depends on this derivation existing
anyway -- a split build feeding hardcoded generators improves nothing.

**Shape D next, because it is the only one that can make macOS real.** A
`macos-latest` job removes both of #1071's causes at the same time (the
symlink survives, ad-hoc codesign works) and is the only place a launch smoke
test can ever run. It is unmetered on a public repo. It also delivers Shape A's
job split as a side effect, which is the honest reason not to pursue A on its
own. Sequence it after C so that if the macOS build starts succeeding, it ships
as `shipped` + `unverified` rather than being silently promoted to equal
standing with Windows.

**The one I would not bother with is Shape B, three independent workflows.**
It buys asynchronous macOS publication. Nothing about macOS is blocked on
scheduling -- it is blocked on #1071 and on the fact that no human has ever
launched a build. B builds a delivery mechanism for a payload that does not
exist and could not be trusted if it did, and pays for it with the
partial-release-that-looks-complete failure mode, a stale-manifest problem that
touches the self-updater's integrity anchor, four documents that need
regeneration triggers, and an amendment to Gate 6. Revisit B only if macOS
becomes buildable **and** a human-in-the-loop verification step must sit between
build and publish -- which is the one scenario where late upload is genuinely
required.

**Shape A on its own is cheap and nearly pointless.** It buys a clearer Actions
UI and about two minutes. Take it when it arrives free with D; do not spend a
week on it alone.

## 10. The smallest useful step

Independent of the redesign, shippable this week, and it makes the next failure
legible on its own. Roughly one day of work, in this order.

**S1. Give `generate-feeds` eyes.** Add a `download-artifact` step for
`build-*` to the `generate-feeds` job. It currently has no way to know what was
built. One workflow step; nothing else changes yet.

**S2. Derive the platform claims.** In `generate_release_metadata.py`, build
`downloads` and `metadata.platforms` from the artifact filenames present rather
than from literals. In `generate_release_manifest.py`, derive `platforms` from
the same `collect_assets()` result that already produces the truthful `assets`
list -- that is a handful of lines in a file that already has a test module.
Refuse to emit a feed with zero required platforms rather than emit an empty
`downloads`.

**S3. Stop the two remaining assertions.** Delete the hardcoded "Windows,
Linux, and macOS" echo in the `notification` job. Make the macOS Gatekeeper
section of the release body conditional on a macOS asset existing.

**S4. Unmask and condition the alias check.** Split `verify-release-urls` into
two jobs so a feed failure stops hiding the alias failure (6.2), and make the
`PDoom.app.zip` assertion conditional on macOS being `shipped` (6.3).

After S1-S4, a release with a failed macOS export publishes Windows and Linux,
advertises exactly two doors, both of which answer, states plainly that macOS
is unavailable and why, and goes **green** -- so the next red run means
something new.

`platform_status` (R5) and the `macos-latest` lane are deliberately **not** in
this step. S1-S4 are worth doing even if every later shape is rejected.
