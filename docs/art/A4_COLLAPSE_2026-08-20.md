## What was actually wrong

`serve_review.py` writes `px:<dir>/<stem>`. The browser gallery wrote
`px:<dir>/<stem>.png`. Both resolve to the same image, and nothing reconciled
them, so the 2026-08-14/15 sweeps left **1,863 files carrying two verdicts each**.

That is not untidiness. `apply_review.py:parse_assets()` builds one work item per
KEY, both keys resolve to the same destination filename, and **1,439 of the pairs
said `keep` under both spellings** -- so the promotion gate reported each file as
contesting its own destination. The gate was right to refuse; it was being fed a
file arguing with itself 1,439 times.

## What was preserved

**373 of the 1,863 pairs disagreed on the verdict** -- a reviewer changing their
mind between the 2026-08-03 gallery sweep and the 2026-08-15 server sessions. In
all 373 the extension-less key is the newer one, so the newer judgement won.

Every losing verdict was **written to the append-only log before it left the
projection** -- 1,863 events carrying `migration: collapse_px_keys` and the full
`prev` value. Recoverable individually:

```
$ grep collapse_px_keys tools/art_review/review_log.jsonl | wc -l
1863
```

Nothing was erased. That follows `revert_action.py`'s reasoning: the log is
append-only and already carries prior values, and erasing a record would be a
second and worse falsification.

## What is still blocking promotion, and why it is not a bug

`blocked: 869 (unresolved-source)` is unchanged, and the report calls it a
"pipeline bug". On this machine it is not. From the tool's own output:

```
blocked-unresolved x242: game_icons        (e.g. gen:game_icons:...)
blocked-unresolved x144: an0807_l1_family  (e.g. gen:an0807_l1_family:...)
```

Those are `gen:` batches whose masters live on the external drive, **by Pip's A1
ruling of 2026-08-19** -- New-Bort is the working machine and the generated
masters are not transferred to it. So the promotion gate cannot resolve a source
for them here, by design, and says so in the voice of a defect.

**Follow-up worth doing:** the gate should distinguish "unresolvable because the
master is off-machine by ruling" from "unresolvable because something is broken".
As it stands it will be permanently red on this machine, and a guard that is
always red carries no information -- this estate's own rule.

## The remaining 100

These are genuine: multiple kept variants of the same base collapsing onto one
game filename, where the variant marker is stripped. A real decision -- un-keep
all but one per base, or rule on a naming change -- and now small enough to
actually work through.

## Non-png was excluded, deliberately

`apply_review.py` resolves a `px:` key by trying `base`, then `base + ".png"`, so
an extension-less key only resolves for `.png`. There are 4,457 png and 9 non-png
under `art_source/`; the nine keep their extension and were not collapsed.

## Why this kept getting worse

The duplicate population was effectively **zero at `2b4d72bc`** and **1,863 four
days later**. It was not a legacy condition being tolerated -- it was a running
process, and every sweep added to it. `canonical_key()` in
`merge_gallery_export.py` already solved the spelling problem but only mapped
INCOMING keys onto existing ones, so every writer that was not the merge tool
walked straight past it.
