# Plan: dev notes and tools on the website (lightweight)

**Status: PROPOSAL for Pip.** Asked for on 2026-10-26 under #1025 ("come up with
a lightweight plan to start making dev notes and tools more available on the
website"). One page on purpose. Nothing here is built yet; the website repo is
not changed by the PR that adds this file.

## Principle

```
+--------------------------------------------------------------------------+
| pdoom1 is the source of truth. The website publishes GENERATED copies,   |
| chosen by an ALLOWLIST, each stamped with the pdoom1 commit it came from.|
| Nothing is hand-copied. Nothing is edited on the website side.           |
+--------------------------------------------------------------------------+
```

Same rule as the 2026-10-26 handbook ruling (pdoom1 owns the master; the website
receives published versions by protocol), applied to every dev doc.

## What to publish first (in order)

1. **Release gates explainer** -- `docs/dev/RELEASE_GATES.md`. Already written to
   be readable from outside; diagrams are plain ASCII, so they render in `<pre>`.
2. **League-cycle handbook** -- `docs/league/LEAGUE_CYCLE_HANDBOOK.md`. Replaces
   the website's hand-written copy and the stale `how-leaderboards-work.md`.
3. **Rulings index** -- `docs/rulings/RULINGS.md`. Already GENERATED by
   `scripts/generate_rulings.py`. Publish the rendered index; link each source
   cell to GitHub rather than publishing the source files themselves.
4. **Commitment calendar** -- `docs/calendar/COMMITMENTS_INDEX.md` and the `.ics`
   (`pdoom1-commitments.ics`), both generated. An `.ics` on the site gives anyone
   a subscribable calendar. Check the owner/notes fields read well in public
   first (see "Not to publish").
5. **Dev tools index** -- `docs/TOOLS.md`, generated by
   `scripts/generate_tools_index.py`. This is the "tools" half of the ask: a
   public list of what each tool does and what invokes it.

Later candidates: `docs/RELEASE_NOMENCLATURE.md`, `docs/GLOSSARY.md`,
`docs/releases/RELEASE_HORIZON.md` (generated).

## How

- Add each path to the design-notes sync's allowlist (or a sibling
  `sync-dev-notes.py` built the same way, rendering into e.g.
  `public/dev-notes/`). One index page lists everything published, generated
  from the manifest.
- Every page carries: source path, pdoom1 commit SHA, render time, and
  "generated -- edit in pdoom1".
- Run the existing scrub (HTML comments, session attributions, TODOs) over every
  file.
- Staleness check on the website side: compare each page's recorded SHA with the
  current file at the chosen ref; fail loudly if behind for more than one cycle.
- pdoom1 can nudge with the existing `pdoom1_docs_update` dispatch type after a
  docs merge (wiring that from pdoom1 CI is a later step, and touches
  `.github/`, so it is not part of this plan's first step).

## Smallest first step

**One allowlist entry: publish `docs/dev/RELEASE_GATES.md` through the existing
design-notes sync, with the source-SHA header.** That proves the path, the
header and the scrub on a page with nothing sensitive in it. Website-side work,
roughly one small PR there. Everything after it is adding lines to the allowlist.

## What NOT to publish

- Anything from the `coordination` repo, or coordination material quoted in
  this repo.
- Personal material: health, family, walking-memo transcripts (`capture:` IDs),
  session logs and day-logs, `docs/archive/`, `SESSION_*`, `TRIAGE_*`.
- Ritual working papers and gate records (`docs/rituals/`) until Pip decides --
  they quote private playtesters and internal disputes. The explainer is the
  public face of them.
- Security-relevant material: server config, API details beyond what players
  already see, credentials guidance.
- Anything not on the allowlist. New directories stay private by default.
